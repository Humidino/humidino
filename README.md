# humidino

Прошивка ESP32-S3 для автоматического контроля микроклимата и вентиляции подпола: опрос 2 датчиков SHT-30 (по одному на двух шинах I2C — подпол и улица), расчёт точки росы и абсолютной влажности, управление вытяжным SSR-реле по алгоритму осушения (с защитой от конденсата и замерзания, антидребезгом), дашборд на LVGL/TFT_eSPI (480x320, ILI9488), локальный веб-интерфейс.

---

## 1. Что нужно перед стартом

- Плата на ESP32-S3 (16 МБ флеш, 8 МБ PSRAM в конфигурации OPI) с распаянными пинами по [config.h](include/config.h).
- Дисплей ILI9488 3.5-inch 480x320 (SPI), 2× датчика SHT-30 (подпол + улица), SSR-реле — подключены согласно пинам в `config.h`.
  Подробная схема подключения (какой пин куда, адреса датчиков, питание, нюансы SSR) — в [docs/WIRING.md](docs/WIRING.md).
- USB-кабель для подключения платы к компьютеру.
- Python 3 (для PlatformIO) — уже используется в этом окружении.

Установка PlatformIO (один раз):

```bash
python -m pip install platformio
```

Проверить, что всё встало:

```bash
python -m platformio --version
```

Дальше все команды `pio ...` ниже можно заменить на `python -m platformio ...`, если короткая команда `pio` не находится в PATH.

## 2. Сборка прошивки

Из корня проекта (`C:\Projects\humidino`):

```bash
pio run -e esp32-s3-devkitc-1
```

Первая сборка займёт несколько минут — PlatformIO скачает тулчейн для Xtensa и все библиотеки (LVGL, TFT_eSPI, WiFiManager и т.д.). Повторные сборки быстрее (десятки секунд).

Если сборка прошла успешно, в конце будет что-то вроде:

```
RAM:   [===       ]  29.7% (used 97444 bytes from 327680 bytes)
Flash: [====      ]  39.2% (used 1231781 bytes from 3145728 bytes)
========================= [SUCCESS] =========================
```

## 3. Заливка на устройство

Подключите плату по USB, затем:

```bash
pio run -e esp32-s3-devkitc-1 -t upload
```

PlatformIO сам найдёт COM-порт платы. Если не находит (или находит не тот) — узнайте порт в диспетчере устройств Windows и укажите явно:

```bash
pio run -e esp32-s3-devkitc-1 -t upload --upload-port COM5
```

Некоторые платы ESP32-S3 требуют зажать кнопку **BOOT** на плате в момент начала прошивки (пока esptool не начнёт печатать `Writing at 0x...`), если автоматический вход в режим загрузки не сработал.

### 3.1. Заливка файловой системы (веб-интерфейс)

Файл [data/index.html](data/index.html) — это страница локального веб-интерфейса. Она **не** зашивается вместе с основной прошивкой, а заливается отдельно на раздел LittleFS:

```bash
pio run -e esp32-s3-devkitc-1 -t uploadfs
```

Без этого шага веб-сервер на устройстве будет отвечать на `/api/state` и `/api/settings`, но по адресу `/` вернёт пустоту — страницы не будет.

### 3.2. Просмотр логов устройства

```bash
pio device monitor
```

(или сразу после прошивки: `pio run -t upload -t monitor`). Выход — `Ctrl+C`.

## 4. Первое включение и настройка Wi-Fi

При первом старте (или если сохранённая сеть недоступна) устройство поднимает собственную точку доступа с именем `humidino` (см. `DEVICE_HOSTNAME` в [config.h](include/config.h)):

1. Подключитесь телефоном/ноутбуком к Wi-Fi сети `humidino`.
2. Обычно автоматически откроется страница настройки (captive portal); если нет — откройте в браузере `http://192.168.4.1`.
3. Выберите домашнюю Wi-Fi сеть, введите пароль, сохраните.
4. Устройство перезагрузится (или переподключится) уже в вашей сети.

Портал настройки активен 180 секунд (`setConfigPortalTimeout`); если за это время сеть не выбрана, устройство повторит попытку — см. `netTask` в [network.cpp](src/network.cpp).

После подключения к сети узнать IP-адрес устройства можно по логам (`pio device monitor`) или в списке клиентов вашего роутера — дальше локальный веб-интерфейс доступен по `http://<IP-устройства>/`.
При первом запуске устройство генерирует и сохраняет отдельный пароль веб-интерфейса. Имя пользователя (`humidino`) и пароль выводятся в Serial при каждом запуске; браузер запросит их при открытии страницы.

## 4.1. Режимы, пресеты, анимация вентиляторов

- **Режимы работы** — переключатель «Авто / Вкл / Выкл» вверху страницы (и виден бейджем на экране платы). Авто — обычный алгоритм по порогам. Ручное вкл/выкл — прямая команда пользователя; защита по замерзанию действует **даже в ручном режиме** (безопасность конструкции важнее любой ручной команды), а вот защита от конденсата и min-pause в ручном режиме намеренно игнорируются — см. комментарии в [relay.cpp](src/relay.cpp).
- **Пресеты** — именованные наборы порогов/таймингов (влажность, гистерезис, заморозка, min-runtime/pause), которые можно сохранить кнопкой «Сохранить как пресет…», применить одним кликом или удалить. Хранятся в NVS одним JSON-блобом (до 8 штук).
- **Анимация** — крутящийся значок вентилятора и на веб-странице (CSS), и на экране платы (LVGL spinner-виджет) появляются, только пока реле реально включено — не декоративная имитация, а прямое отражение состояния `relay.on`.

**Экран на плате — тачскрин (XPT2046, резистивный)**: физических кнопок нет, но экран не только показывает статус — на нём есть своя навигация (внизу, 4 вкладки) с тем же самым функционалом, что и в веб-интерфейсе:

- **Main** — дашборд (сетка зон, баннер статуса) плюс кнопки переключения режима «АВТО / ВКЛ / ВЫКЛ».
- **Settings** — пороги и тайминги осушения (целевая влажность, гистерезис, защита от замерзания, min-runtime/pause) — редактируются степперами `+`/`-`.
- **Presets** — список сохранённых пресетов с «Применить»/«Удалить» на каждой строке и формой сохранения текущих настроек под новым именем.
- **Stats** — сводка и список последних запусков реле (см. п. 4.2 ниже).

Подписи вкладок внизу — латиницей (Main/Settings/Presets/Stats): встроенный в LVGL шрифт по умолчанию не содержит кириллицу, а весь остальной текст интерфейса кириллический за счёт отдельно подключённых шрифтов (см. [fonts/fonts.h](src/fonts/fonts.h)). Экранная клавиатура (для имени пресета) — тоже только латиница/цифры; кириллические значения, заданные через веб-интерфейс, на экране отображаются корректно, просто ввести их с самого экрана нельзя.

Wi-Fi (домашняя сеть) сюда не входит и настраивается только через отдельный captive portal при первом включении (см. п. 4) — это осознанно не продублировано на тачскрине.

**Первое включение экрана потребует калибровки тача** — прошивка один раз попросит коснуться нескольких меток, после чего калибровка сохраняется в NVS и больше не запрашивается. Подробности подключения тача (пины, нюансы) — в [docs/WIRING.md](docs/WIRING.md), §2.

## 4.2. Аналитика и статистика

Ответ на «пришёл на следующий день — сколько было запусков и какая была влажность»: каждый цикл включения/выключения реле пишется в журнал (кольцевой буфер на `RUN_LOG_CAPACITY` = 2000 записей на LittleFS, см. [run_log.h](src/run_log.h)/[run_log.cpp](src/run_log.cpp)) — время начала и конца, показания обоих датчиков (подпол + улица) в оба момента и причина остановки (по графику, вручную, защита от мороза/конденсата, ошибка датчика, обрыв из-за перезагрузки). При заполнении буфера самые старые записи затираются новыми — реалистично это несколько недель-месяцев истории при обычной частоте циклов.

- **Время.** Записям нужны реальные метки времени, поэтому прошивка синхронизирует время по NTP (`pool.ntp.org`) сразу после подключения к Wi-Fi (см. [time_sync.h](src/time_sync.h)) — это единственное место в проекте, которому нужен выход в интернет, а не только локальная сеть. Без него (например, роутер без интернета) журнал продолжает работать как обычно, просто новые записи получают метку «время не синхронизировано», и группировка «сегодня» недоступна, пока синхронизация не пройдёт. Устройство не хранит часовой пояс — журнал и JSON-API всегда работают в UTC; для группировки «сегодня» в сводке статистики и часов на экране платы есть отдельная константа `LOCAL_TZ_OFFSET_SEC` в [config.h](include/config.h) (по умолчанию МСК, UTC+3) — поменяйте её под свой пояс. Веб-интерфейс на часовой пояс устройства не полагается: браузер сам переводит эпоху в локальное время.
- **Экран платы** — 4-я вкладка **Stats**: сводка (запусков сегодня, время работы сегодня, всего запусков за всё время) и прокручиваемый список последних ~20 циклов с показаниями на старте/остановке каждого.
- **Веб-интерфейс** — раздел «Аналитика и статистика»: те же сводные цифры, столбчатый график запусков за последние 14 дней (чистый inline SVG, без библиотек) и таблица последних записей журнала.
- **API** — `GET /api/history/summary` (сводка) и `GET /api/history?limit=N&offset=M` (записи от самой свежей, лимит на сервере — 200 за один запрос) поверх формата, который уже отдаёт `Telemetry::buildHistoryJson()` в [telemetry.cpp](src/telemetry.cpp).

Как и остальной локальный веб-интерфейс, раздел аналитики можно потестировать без устройства — мок-сервер (см. п. 5.1) генерирует правдоподобную историю запусков за последние ~10 дней.

## 5. Тестирование интерфейса БЕЗ заливки на устройство

Тут два разных интерфейса, и с ними по-разному:

### 5.1. Локальный веб-интерфейс (data/index.html) — можно потестировать прямо сейчас

Веб-страница — это обычные HTML/CSS/JS, которые обращаются к REST API (`/api/state`, `/api/settings`, `/api/presets`, `/api/history`, `/api/history/summary`). На реальном устройстве эти эндпоинты отдаёт ESP32, но их легко подменить локальным мок-сервером — я уже сделал такой в [tools/mock_web_server.py](tools/mock_web_server.py). Он:

- отдаёт `data/index.html` как есть;
- генерирует правдоподобные (но не настоящие) показания датчиков, слегка «плавающие» во времени;
- каждые 8 секунд переключает состояние реле по кругу через все 6 состояний (`ОЖИДАНИЕ` → `РАБОТА` → `ЗАПРЕТ ПО КОНДЕНСАТУ` → `ЗАПРЕТ ПО МОРОЗУ` → `ОЖИДАНИЕ` → `ОШИБКА ДАТЧИКА` → ...) — включая анимацию вентилятора (крутится только на `РАБОТА`) и все цвета баннера;
- поддерживает переключение режима (Авто/Вкл/Выкл — реально сохраняется и переживает перезагрузку страницы);
- поддерживает пресеты: `GET/PUT /api/presets`, `POST /api/presets/apply` — можно сохранять, применять и удалять прямо в браузере;
- отдаёт правдоподобную (сгенерированную один раз при старте мок-сервера) историю запусков за последние ~10 дней на `/api/history` и `/api/history/summary` — можно посмотреть раздел «Аналитика и статистика» (график, таблицу) без устройства.

Запуск:

```bash
python tools/mock_web_server.py
```

и открыть в браузере **http://localhost:8000/**. Порт можно поменять: `python tools/mock_web_server.py 8123`.

Это не зависит от PlatformIO/ESP32 вообще — только стандартная библиотека Python. Так можно проверить вёрстку, поведение при ошибке датчика (бейдж `ERR`), смену цвета/текста баннера и отправку формы настроек — всё до того, как в руках вообще появится плата.

### 5.2. Графический дашборд на дисплее (LVGL/TFT_eSPI) — так просто не потестировать

А вот это уже не браузерная страница, а код, который рисует пиксели напрямую в SPI-дисплей через TFT_eSPI (см. [display.cpp](src/display.cpp), [ui_dashboard.cpp](src/ui_dashboard.cpp)) — в браузере это не откроется. Варианты:

1. **Реальное железо** — единственный способ, для которого всё уже готово.
2. **PC-симулятор LVGL** — LVGL официально поддерживает сборку под SDL2 и запуск на компьютере (окошко с «дисплеем» вместо реального экрана). Это возможно, но потребует отдельного окружения PlatformIO (`platform = native` или сборка под SDL, свой `lv_conf.h` под симулятор, замену TFT_eSPI-специфичного кода в `display.cpp` на SDL-бэкенд) — то есть отдельную ветку кода, а не «просто запустить». В текущем проекте этого нет.

Если хотите посмотреть именно дашборд без платы — могу собрать LVGL PC-симулятор отдельным окружением (это дополнительная работа, скажите, если нужно). Пока что самый быстрый способ проверить, что визуально всё работает как задумано — веб-мок из п. 5.1: у него те же данные, тот же баннер и цвета, просто в браузере вместо TFT-экрана.

## 6. Что не проверено на реальном железе

Код писался и правился без доступа к устройству и без возможности собрать прошивку локально (PlatformIO не может скачать тулчейн/библиотеки в этом окружении — сеть недоступна для его реестра) — **ни разу не прошивался, не тестировался на физической плате и даже не проходил полную компиляцию** этой машиной. Перед вводом в эксплуатацию обязательно проверить:

- **Соберите прошивку в первую очередь** (`pio run -e esp32-s3-devkitc-1`, п. 2) в окружении с доступом к интернету, прежде чем заливать на плату — особенно код тач-интерфейса (`ui_root.cpp`, `ui_settings_screen.cpp`, `ui_presets_screen.cpp`, `ui_stats_screen.cpp`, `ui_keyboard.cpp`) — он использует виджеты LVGL (spinbox, keyboard, textarea), которые в проекте раньше не применялись и не собирались ни разу.
- Ориентацию/поворот дисплея (`g_tft.setRotation(1)` в [display.cpp](src/display.cpp) — может потребовать 0/2/3). Тач откалиброван под ту же ориентацию, что задана на момент калибровки — если ориентацию меняете, калибровку тача нужно будет сбросить и пройти заново.
- Реальную работу PSRAM (сборка использует вариант `qio_opi`, но фактическая инициализация проверяется только на плате).
- Первую калибровку тачскрина (см. п. 4.1 выше и [docs/WIRING.md](docs/WIRING.md), §2/§8) — устройство должно быть физически доступно для касания при первом включении.
- Тайминги min-runtime/min-pause удобно на первое время уменьшить в [config.h](include/config.h) для ускоренной стендовой проверки state machine реле.
- Юнит-тесты `climate_math` (`pio test -e native`) требуют локального gcc/g++ (не установлен в этом окружении) — формулы проверены вручную, но тест-раннер не запускался.
- **Журнал запусков** (`run_log.h`/`run_log.cpp`, п. 4.2) — чтение/запись на реальном LittleFS не проверялись на железе: работа с файлом через `File::seek()`/`r+` (обновление заголовка и отдельных записей на месте, без перезаписи всего файла), корректность после реальной потери питания посреди записи, и то, что первое создание файла (`RUN_LOG_CAPACITY` = 2000 нулевых записей, один раз за всё время жизни устройства) укладывается в разумное время при первом включении.
- **NTP-синхронизация** (`time_sync.h`) — `configTime()` вызывается один раз при первом подключении к Wi-Fi; не проверялось поведение при недоступном NTP-сервере (роутер без интернета, только локальная сеть) — по коду журнал должен продолжать писать записи с меткой «время не синхронизировано», но живьём не наблюдалось.

## 7. Шпаргалка команд

| Команда | Что делает |
|---|---|
| `pio run -e esp32-s3-devkitc-1` | Собрать прошивку |
| `pio run -e esp32-s3-devkitc-1 -t upload` | Собрать и залить прошивку на плату |
| `pio run -e esp32-s3-devkitc-1 -t uploadfs` | Залить веб-интерфейс (data/) на LittleFS |
| `pio device monitor` | Смотреть serial-логи устройства |
| `pio run -t upload -t monitor` | Залить и сразу открыть логи |
| `python tools/mock_web_server.py` | Локальный просмотр веб-интерфейса без устройства |
